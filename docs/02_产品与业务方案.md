# 02 — 产品与业务方案

> 当前是 Product Brief。产品链消费标准化 DetectionResult，不与竞赛评分内核耦合。

## 1. 产品定位

山水智鉴不再以“首次实现识别—核验—整改—销号”作为差异化。真实采购和运行案例已经证明这些环节存在。

当前定位为：

> **可嵌入既有河湖监管平台的多模型适配、证据编排与反馈评测中间件。**

产品由三部分组成：

```text
开放治理事件中间件
＋
异常证据核验工作台
＋
既有平台 API 集成
```

## 2. 目标客户与用户

### 采购或建设决策者

- 水利局、河长办和流域管理机构；
- 城市治理、市政信息和生态环境部门；
- 水库、湖区和河道运营单位；
- 城市信息化总包商和系统集成商。

### 日常使用者

| 角色 | 核心任务 |
|---|---|
| AI 监管或值班人员 | 查看证据、核验告警、过滤误报 |
| 河湖管理人员 | 判断类型、严重度、辖区和责任主体 |
| 巡查与处置人员 | 现场核查、拍照和结果回传 |
| 算法运维人员 | 接入模型、分析 Bad Case、管理版本 |
| 系统集成商 | 将标准事件同步到既有业务系统 |
| 管理者 | 查看有效告警、核验效率、处置和复发情况 |

## 3. 核心对象链

```text
ModelAdapter
    ↓
DetectionResult
    ↓
EvidenceAssembler
    ↓
EvidenceBundle
    ↓
AlertEngine
    ↓
AnomalyAlert
    ↓
人工确认 / 驳回及原因记录
    ↓
GovernanceEvent 或外部系统事件
    ↓
ResponsibilityRouter
    ↓
WorkOrder
    ↓
现场反馈与复核
    ↓
ReplayCase / Eval Dataset
```

### 对象边界

- `DetectionResult`：单次模型推理结果；
- `EvidenceBundle`：同一问题的多帧、多源和人工证据；
- `AnomalyAlert`：经过规则、持续性和去重后的待核验告警；
- `GovernanceEvent`：人工确认后进入正式治理流程的事件；
- `WorkOrder`：事件拆分出的处置任务；
- `ReplayCase`：模型、人工和处置全过程记录。

## 4. 人机边界

| 环节 | 系统自动完成 | 人工责任 |
|---|---|---|
| 模型推理 | 是 | 不直接承担治理结论 |
| 证据聚合和重复候选合并 | 是 | 可调整或拆分 |
| 告警生成 | 是 | 必须确认或驳回 |
| 事件创建 | 草稿 | 人工确认 |
| 责任主体推荐 | 建议 | 管理人员确认 |
| 工单创建 | 预填 | 人工下发 |
| 现场完成 | 否 | 上传证据并提交 |
| 复核关闭 | 辅助 | 人工最终确认 |

## 5. V0 范围

数据开放前只实现：

```text
DetectionResult
→ EvidenceBundle
→ AnomalyAlert
→ 人工确认 / 驳回
→ 原因记录
```

V0 页面只保留：

1. **异常证据核验工作台**：原始影像、预测结果、证据时间线、确认或驳回；
2. **最小事件 Replay**：展示模型版本、证据、人工动作和状态变化。

首个稳定 Baseline 后再实现 GovernanceEvent、ResponsibilityRouter、WorkOrder、现场反馈和完整 Replay。

## 6. 产品交付形态假设

| 形态 | 适用客户 | 当前状态 |
|---|---|---|
| 独立轻量核验平台 | 缺少现成 AI 核验能力的区县或运营单位 | 待验证 |
| 既有平台能力模块 | 已有河长制、一网统管或工单平台 | 优先假设 |
| 算法治理中间件 | 系统集成商、算法厂商和市政信息公司 | 优先假设 |
| 专项技术与运营服务 | 遥感核查、视频巡检、模型适配和年度报告 | 已有市场证据 |

## 7. 可交付服务

- 模型适配与评测；
- 水域异常 AI 识别；
- 人工核验工作台；
- 既有平台 API 集成；
- 专项数据治理和模型迭代；
- 问题图斑、核查报告和整改复核成果生产。

## 8. 核心产品指标

数据开放和原型测试后验证：

- 模型接入时间；
- DetectionResult Schema 通过率；
- 重复告警压缩率；
- 人工核验平均耗时；
- 确认/驳回原因完整率；
- 多源证据完整率；
- Replay 记录完整率；
- 反馈样本进入 Eval 数据集的比例。
