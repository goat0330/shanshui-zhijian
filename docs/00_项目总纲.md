## 2. 两个比赛的关系

| 维度 | IAIC | 智慧城市大赛 |
|---|---|---|
| 核心问题 | 指定任务能否有效识别并合法提交 | 产品能否形成真实治理价值 |
| 主要交付 | 数据 Adapter、预测、JSON、评分、消融、代码 | 产品方案、原型、业务闭环、实施与商业材料 |
| 共享资产 | 数据、模型、预处理、Run、Bad Case | 同左，并补充证据、事件和业务流程 |
| 独立对象 | PredictionRecord、SubmissionBundle | Observation、Candidate、Event、Review |
| 禁止依赖 | 人工审核和工单状态 | 官方提交顺序与评分结果 |

## 3. 双链领域架构

### 3.1 产品治理链

```text
Source
→ Asset
→ Observation
→ DetectionCandidate
→ AnomalyEvent
→ ReviewDecision
→ AlertDelivery
→ IncidentCase / 外部系统
```

### 3.2 比赛评测链

```text
CompetitionInput
→ InferenceTask
→ PredictionRecord
→ SubmissionBundle
→ SubmissionAttempt
```

### 3.3 共享与隔离

共享：

- Asset；
- ModelRun；
- 预处理和推理组件；
- 权重、配置、代码和数据版本；
- 通用几何、时间与质量工具。

隔离：

- 产品链可以合并、拆分和重审 Candidate/Event；
- 比赛链必须保持官方样本 ID、顺序、输出数量与 Schema；
- ReviewDecision 不得修改 PredictionRecord；
- SubmissionBundle 不从 Event 或 WorkOrder 生成。

## 4. 产品机会

成熟市场已经存在“发现—核查—交办—整改—复核”闭环。山水智鉴不以该闭环本身作为首创，而聚焦：

1. **模型开放接入**：赛事模型、自研模型和第三方算法通过 Adapter 接入；
2. **证据统一组织**：视频、遥感、文本和人工核查形成可追溯 Evidence；
3. **人机研判分层**：模型只产生 Observation/Candidate，人决定 Event 的业务含义；
4. **评测与反馈回流**：Review 与 Bad Case 服务模型评估，但不污染原始预测；
5. **既有平台集成**：通过 API 或组件接入河长制、一网统管和第三方工单系统。

## 5. 当前范围

### P0：必须完成

- 遥感验证集和指标；
- 真 COG 瓦片服务；
- 最小领域契约；
- Mock/官方评测导出链；
- 状态和分支同步；
- 高点视频单视频最小纵切设计冻结。

### P1：首个稳定 Baseline 后

- 高点视频 MP4 → Candidate → Evidence → Review；
- PostGIS 迁移评估；
- React 五页壳；
- Outbox、幂等和并发控制。

### 暂不纳入

- 完整微服务和 Kubernetes；
- Kafka/Flink；
- 完整 eoAPI 云基础设施；
- 多路实时视频平台；
- 完整河长制和工单中心；
- 大型 RAG、多 Agent 业务编排；
- 无证据的复杂模型堆叠。

## 6. 当前事实

已验证：

- GEE 多源数据进入本地 Pipeline；
- S1 双时相水体变化可输出图斑；
- EPSG:4545 和地理重投影；
- `NO_DATA / NO_CHANGE / DETECTED` 三态；
- FastAPI、SQLite 与演示页面；
- 服务重启后记录仍存在。

未验证：

- 当前候选精度；
- 正式赛题标签与指标；
- 高点视频识别；
- 真实 TiTiler 瓦片链；
- 生产级并发、安全和部署。

## 7. 核心原则

1. 产品链与比赛链硬隔离；
2. 模型观测不直接成为治理事实；
3. 生命周期、质量、证据和错误正交；
4. 所有结论可追溯到 Asset、Run、Config 和 Model；
5. 先模块化单体，后按负载和团队边界拆分；
6. 先建立验证集，再优化模型；
7. 先修复真实数据链，再重做界面；
8. 所有数字有唯一事实源；
9. 代理数据和官方数据严格隔离；
10. 目标架构不等于当前实现。
