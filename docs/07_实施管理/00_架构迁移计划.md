# 架构迁移计划

## 1. 迁移目标

将当前 V0：

```text
Pipeline → DetectionResult → Alert/Event/WorkOrder
```

渐进迁移为：

```text
产品：Asset → Observation → Candidate → Event → Review
比赛：Input → InferenceTask → PredictionRecord → SubmissionBundle
```

不进行一次性重写，不阻塞现有演示。

## 2. 迁移策略

### 阶段 A｜文档和契约冻结

交付：

- 双链边界；
- 最小对象字段；
- JSON 示例；
- `DetectionResult` 兼容映射；
- 契约测试清单。

完成定义：

- 产品和比赛成员对同一字段含义无歧义；
- Review 不进入 PredictionRecord；
- 生命周期、质量和错误字段分开。

### 阶段 B｜兼容适配器

新增逻辑：

```text
DetectionResult
├─ ProductCompatibilityAdapter → Observation + Candidate
└─ CompetitionCompatibilityAdapter → PredictionRecord
```

旧 API 和页面继续使用，新增对象先双写或离线转换。

完成定义：

- 同一 DetectionResult 映射稳定；
- 新对象可追溯到旧 ID；
- 旧页面不受影响；
- 映射具备 golden test。

### 阶段 C｜独立评测链

实现：

- CompetitionInputAdapter；
- InferenceTask；
- PredictionRecord；
- SubmissionBundle；
- Schema Validator；
- SubmissionAttempt。

完成定义：

- 样本 ID 和顺序稳定；
- 空预测合法；
- 产品 Review 不改变提交包；
- 同配置重复导出一致。

### 阶段 D｜产品领域链

实现：

- Asset；
- Observation；
- Candidate；
- Event；
- ReviewDecision；
- Evidence。

现有 Alert、Event 和 Replay 通过兼容层逐步迁移。

完成定义：

- 原始模型输出不可被 Review 覆盖；
- Event 合并和拆分可审计；
- Evidence 可追溯；
- 并发 Review 有冲突处理。

### 阶段 E｜存储与任务可靠性

触发后实施：

- PostgreSQL/PostGIS；
- Alembic；
- 任务租约；
- inbox/outbox；
- 乐观锁；
- Worker 重试和死信；
- 追加式审计。

不要为了“架构先进”提前迁移。

### 阶段 F｜前端迁移

Jinja2 页面继续可运行。React 先建立五页壳，再逐页替换。

禁止：

- 在 API 和契约未稳定时大规模重写前端；
- 前端直接读取本地 GeoTIFF、数据库文件或模型 SDK；
- 评测页读取 Review 状态生成提交。

## 4. Gate

### F0 契约冻结

- Schema；
- 示例；
- 映射；
- 契约测试；
- 决策记录。

### F1 本地可运行

- 一键 Pipeline；
- Run Manifest；
- 真瓦片；
- 验证集与指标；
- 服务启动说明。

### F2 一致性与失败恢复

- 重复导入幂等；
- 并发审核；
- Worker 中断恢复；
- 数据库迁移；
- 审计不可覆盖。

### F3 高点视频闭环

- 授权视频；
- 时间戳；
- ROI；
- Candidate；
- Evidence；
- Review；
- 断网/失败说明。

### F4 评测链闭环

- Adapter；
- PredictionRecord；
- Bundle；
- Validator；
- SubmissionAttempt；
- 与产品链隔离测试。

### F5 双场景演示

- 遥感场景；
- 视频场景；
- 人工研判；
- 评测实验室；
- 事实边界和不可宣称内容。
