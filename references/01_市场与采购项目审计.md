## 5.1 审计方法与证据规则

### 5.1.1 本轮不把“新闻案例”直接等同于“成熟产品”

本轮把公开对象分为四种状态：

| 状态 | 判断标准 |
|---|---|
| **M1 需求/采购阶段** | 已发布采购意向、采购公告或场景需求，但尚无公开运行结果 |
| **M2 试点/建设阶段** | 已中标、签约、测试或处于建设调试期，尚未形成稳定运营数据 |
| **M3 稳定运营阶段** | 已公开持续运行、闭环处置或可量化效率指标 |
| **M4 标准化复制阶段** | 除持续运行外，已形成市级标准、跨区域部署或专业化运营机制 |

### 5.1.2 证据优先级

1. **A级：政府采购公告、合同公告、中标公告、采购意向**；
2. **B级：政府部门、国资平台、水利或生态环境主管部门发布的运行信息**；
3. **C级：主流媒体或行业媒体对运行方式的补充报道**；
4. **D级：厂商宣传材料**，只能作为线索，不能单独支撑关键判断。

### 5.1.3 每张产品卡必须区分三类内容

- **公开事实**：来源能够直接证明；
- **审计判断**：根据公开材料作出的产品判断；
- **公开缺口**：现有材料没有说明，不能替项目方补写。

| **业务事件** | 非法采砂、河面漂浮物及其他河湖异常问题。公开口径称已识别 **20 余类问题**。 |

| **采购/交付模式** | 公开材料证明了运行结果，但未披露采购公告、合同金额、建设厂商、算法供应商及运维合同。不能据此判断是自建、总包建设还是购买巡检服务。 |
| **已有优势** | 已经越过“能不能识别”的演示阶段，进入可量化的巡检、交办和销号运营；同时公开了里程、工时、告警量和处置时长等业务指标。 |
| **公开材料缺口** | 未披露模型名称与版本、类别定义、准确率、每类误报率、连续帧去重规则、人工驳回原因、同一问题重复告警合并逻辑、Bad Case 回流方式和对外接口。 |
| **对山水智鉴的启示** | 山水智鉴不能只输出检测框，应把“告警去重、事件生成、责任交办、销号复核、运营指标”设计为正式产品对象。巴南证明闭环台账是政府能够感知的价值，但其公开材料未证明模型与流程是否开放、可替换、可复盘，这正是开放中间层的切入点。 |

| **公开材料缺口** | 未披露在线平台、API、模型、自动化比例、图斑数据格式、事件唯一标识、核查人员操作记录、同一问题跨期追踪方式和数据是否可持续沉淀。 |

# 5.4 十个案例的横向结论

## 5.4.1 政府真正购买的不是“识别框”，而是治理成果

十个样本中，最清晰的付费对象包括：

- 问题图斑与专题图册；
- 经无人机核验的问题记录；
- 整改后的复核报告；
- 自动预警和推送服务；
- 机巢、边缘网关与专项识别程序；
- 常态化巡检运营；
- 工单、处置和销号台账；
- 跨区域标准和运营机制。

郑州最能说明这一点：公开采购要求可以完全不把 AI 写成验收项，但会明确要求问题图册、航拍核查和整改复核。产品价值必须落在可被管理部门使用和验收的成果上。

## 5.4.2 市场通常围绕具体问题采购，不采购“万能模型”

- 云南采购高点视频中的“四乱”、碍洪障碍物和漂浮物识别；
- 太湖流域采购水葫芦专项识别、边缘网关和无人机设备；
- 山南要求适应高海拔环境并结合本地数据定制训练；
- 绍兴围绕地方巡河任务形成 9 类定制算法。

因此，山水智鉴的正确方向不是把一个大模型包装成所有水域问题的唯一识别器，而是建立可接入、可替换、可评测的模型插件体系。

## 5.4.3 “告警”和“治理事件”在市场上经常被混写

公开材料普遍使用“识别、预警、推送、工单、事件”等词，但只有部分项目明确证明了核验、整改和销号。

| 闭环公开程度 | 案例 |
|---|---|
| **公开证明较完整** | 巴南、宁波、绍兴、新洲 |
| **以专业服务成果完成核查与复核** | 郑州 |
| **主要公开到告警或监测阶段** | 云南、太湖、山南 |
| **处于需求或试点，闭环尚待验证** | 无锡、怀化 |

这说明山水智鉴必须在数据结构上强制区分：

```text
DetectionResult != AnomalyAlert != GovernanceEvent != DisposalTask
```

## 5.4.4 边缘—云端协同已有真实采购，但往往是专项交付

太湖项目公开采购机巢、无人机、智能边缘网关和水葫芦识别程序；怀化试点也把边缘终端和本地化模型作为核心组成。真实项目更关注：

- 设备是否接得上；
- 弱网或断网时能否运行；
- 现场是否能快速筛选有效数据；
- 模型如何更新；
- 边缘结果如何回传并进入业务流程。

因此“边缘计算”不能只作为架构图中的一个框，应形成设备适配、模型下发、版本管理、运行监控和结果同步能力。

## 5.4.5 智能体需求正在出现，但成熟产品证据仍不足

无锡明确提出水利智能体、污染溯源和多域无人系统；怀化提出本地模型与水利行业智能体。但现有公开材料仍没有证明：

- Agent 可以调用哪些工具；
- 每次研判依据是什么；
- 如何处理模型冲突；
- 什么时候必须人工确认；
- 建议是否被采纳；
- 错误建议如何回放和评测。

因此，“行业智能体”是值得布局的方向，但当前不能只靠聊天界面或自然语言总结来证明。

# 5.5 山水智鉴应形成的产品中间层

## 5.5.1 核心价值主张

> **从模型识别结果，到可核验、可处置、可复盘的治理事件。**

```text
任意视频、遥感或基座模型
              ↓
统一 DetectionResult
              ↓
连续帧、时空与多源证据聚合
              ↓
EvidenceBundle
              ↓
去重、持续性验证、区域与风险规则
              ↓
AnomalyAlert
              ↓
人工核验与原因记录
              ↓
GovernanceEvent
              ↓
处置任务与现场反馈
              ↓
Replay、模型评测与流程复盘
```

## 5.5.2 第一版必须具备的九项能力

### 1. 数据与模型适配器

接入：

- IAIC 指定基座模型；
- MMDetection 等检测模型；
- 遥感分割模型；
- 第三方厂商接口；
- 后续水葫芦、蓝藻、水草等专项模型；
- 高点视频、无人机、遥感切片和历史文件。

### 2. 统一 DetectionResult

至少记录：

- 来源设备与数据；
- 模型名称和版本；
- Prompt 或推理配置版本；
- 类别、置信度和空间范围；
- 时间、坐标与原始证据引用；
- 推理耗时和运行节点。

### 3. EvidenceBundle

把单帧结果扩展为可判断的证据包：

- 连续帧；
- 同点位历史记录；
- 遥感切片；
- 多摄像头或多设备结果；
- 规则命中；
- 人工补充材料。

### 4. 告警去重与持续性判断

避免每一帧、每一次巡航都生成新工单。至少支持：

- 时间窗口合并；
- 空间邻近合并；
- 同类别持续事件；
- 已整改事件重新出现；
- 同一目标跨设备合并。

### 5. 告警与事件分离

- **DetectionResult**：模型观察；
- **AnomalyAlert**：满足告警规则；
- **GovernanceEvent**：经过证据聚合或人工确认，正式进入治理流程；
- **DisposalTask**：面向责任主体的执行任务。

### 6. 人工核验与原因结构化

人工操作不能只保留“通过/驳回”，还要记录：

- 误识别；
- 重复告警；
- 非治理对象；
- 已处置但数据未更新；
- 证据不足；
- 类别错误；
- 位置错误；
- 其他原因与说明。

### 7. 处置闭环与现场反馈

支持：

- 交办；
- 接收；
- 到场；
- 处理中；
- 整改完成；
- 复核；
- 销号；
- 退回重办；
- 重复发生。

### 8. Replay 与模型评测

把人工驳回、现场核查和整改结果转化为：

- Bad Case；
- 回放样本；
- 版本对比集；
- 区域化评测集；
- 误报和漏报分析；
- 规则与阈值调优依据。

### 9. Agent 工具调用与决策留痕

Agent 至少应能够调用：

- 视频与图像识别；
- 遥感检索；
- 地图与空间分析；
- 历史事件查询；
- 规则引擎；
- 污染线索关联；
- 工单创建与状态查询；
- 报告生成。

每次调用必须保留输入、输出、模型/工具版本、判断依据、人工确认和最终结果。

# 5.6 对现有市场的补充定位

山水智鉴不应宣称：

> 首次利用 AI、视频和无人机开展智能巡河。

更可信的差异化表达是：

> **山水智鉴面向已有视频、遥感、无人机和第三方算法，提供从 DetectionResult 到 GovernanceEvent 的开放事件中间层，通过证据聚合、告警去重、人工核验、处置闭环和 Replay 评测，使不同模型产生的结果能够被核验、交办、复盘并持续改进。**

它不是替代现有河长平台、无人机平台或识别算法，而是补足它们之间最容易断裂的部分：

```text
多源感知
  ×
多模型输出
  ×
事件判断
  ×
治理流程
  ×
模型反馈
```

# 5.7 下一轮产品审计的固定检查项

下一轮不再增加案例数量，而是围绕这 10 个对象继续补证。每个项目统一检查以下内容：

| 维度 | 需要继续核查的问题 |
|---|---|
| **项目状态** | 是否已签约、上线、验收、续费或停止 |
| **使用角色** | 谁看告警、谁核验、谁派单、谁销号 |
| **输入数据** | 视频、无人机、遥感、传感器和历史数据如何接入 |
| **模型管理** | 模型名称、版本、阈值、区域配置和更新方式 |
| **证据结构** | 原始帧、连续帧、切片、轨迹和人工材料如何关联 |
| **事件化** | 如何去重、合并、判断持续性和生成唯一事件 |
| **人工审核** | 驳回原因是否结构化，是否进入训练与评测 |
| **处置闭环** | 是否存在交办、整改、复核、销号和退回重办 |
| **运营指标** | 有效告警率、处置时长、整改率、重复发生率、在线率 |
| **开放能力** | API、事件 Schema、第三方模型接入和既有系统集成 |
| **Agent 能力** | 工具调用、权限、人机边界、判断证据和建议采纳率 |
| **商业模式** | 硬件采购、软件建设、年度服务、运营服务或组合模式 |

# 5.8 本轮最终判断

1. **IAIC 主要验证算法识别层，但市场验收通常发生在业务处置层。**
2. **政府愿意为问题图斑、核查报告、边缘设备、专项模型、闭环工单和长期运营付费。**
3. **成熟案例已经证明巡检、预警、交办和销号不是创新点本身。**
4. **真正仍缺乏公开证明的是模型可替换、证据可追溯、事件去重、人工原因结构化、结果反哺和 Agent 决策评测。**
5. **山水智鉴应把这些缺口收束为一个开放、可核验、可回放的治理事件中间层。**
6. **比赛版本先证明 DetectionResult 可靠，智慧城市版本再证明它能够稳定转化为 GovernanceEvent。**

## 3. 产品假设修正

### 不再宣称

> 首次把 AI 识别结果送入人工核验、整改和销号闭环。

### 当前定位

> 把比赛指定模型、自研视频模型、遥感模型及第三方算法统一转换为标准化、可追踪、可评测的异常证据，并以模块化方式接入既有核查和治理流程。

### 三个“开放”

```text
模型开放接入
任意模型 → ModelAdapter → DetectionResult

证据开放组合
视频 / 遥感 / 文本 / 人工 → EvidenceBundle

反馈开放回流
确认 / 驳回 / 处置 / 复核 → Replay / Eval
```

## 4. 六个产品缺口假设

| ID | 假设 | 当前状态 | 表述边界 |
|---|---|---|---|
| H-001 | 多模型结果需要统一接口 | 部分证实 | 已有多源多模型建设，但公开标准不足 |
| H-002 | 连续检测需要告警去重 | 公开材料未说明 | 不能写成市场没有 |
| H-003 | 多源结果需要统一证据包 | 部分证实 | 市场有多源核验，具体数据结构未公开 |
| H-004 | 人工确认与驳回原因需要结构化 | 公开材料未说明 | 作为产品设计假设 |
| H-005 | 处置结果应进入模型 Eval | 公开材料未说明 | 作为可验证创新 |
| H-006 | 既有平台需要可插拔模型适配 | 部分证实 | 多厂商集成需求存在，接口开放度待验证 |

## 5. 最终市场结论

1. 市场已经存在识别、人工核验、整改复核和销号；
2. 政府购买的是问题图斑、核查报告、处置结果、运营服务和平台能力；
3. 产品机会不是补一个“别人没有的流程环节”；
4. 更可信的机会是让模型和业务解耦，并让证据和反馈具有统一标准；
5. 山水智鉴应优先作为既有平台能力模块或算法治理中间件，而不是完整硬件和平台总包商。
